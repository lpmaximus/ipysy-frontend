# 📄 1. Contexto e Motivação

A análise comparativa do repositório MiroFish (março de 2026) revelou uma oportunidade arquitetural relevante para o iPYSY: a adição de uma camada de simulação narrativa que explique o consenso probabilístico produzido pelo Core v3.2, sem substitui-lo. O MiroFish é um simulador multi-agente baseado em LLM (framework OASIS + Zep Cloud) que gera "previsões" como narrativas interpretativas emergentes. Sua fragilidade estrutural é a ausência de fundamento matemático auditável — output qualitativo sem ancoragem probabilística.

O iPYSY possui o inverso: fundamento matemático robusto (IGCI, Brier Score, reputação calibrada) sem camada explicativa. A combinação correta desses dois elementos — probabilidade auditável + explicação narrativa — representa um diferencial de produto impossível de ser rapidamente replicado por concorrentes.

Este ADR formaliza a decisão arquitetural de implementar o iPYSY Decision OS como um novo microserviço (scenario-engine, porta 9018) que opera estritamente acima do Core v3.2, consumindo suas saídas de forma passiva e nunca interferindo em seu cálculo. O ADR é registrado com status DEFERRED porque as dependências estruturais necessárias para que a camada narrativa entregue valor real ainda não estão satisfeitas no momento da redação.

> **PRINCÍPIO ARQUITETURAL CENTRAL O scenario-engine NUNCA modifica, recalcula ou interfere no Core v3.2. Opera exclusivamente como consumidor passivo do tópico ipysy.consensus.updated. A probabilidade produzida pelo IGCI é a única fonte de verdade — a narrativa é sempre apresentada como explicação, jamais como previsão alternativa.**

# 📄 2. Definição do Problema

> **PROBLEMA CENTRAL:** O iPYSY produz consenso probabilístico auditável (IGCI), mas não explica causalmente por que determinada probabilidade foi alcançada. Clientes B2B — fundos, gestores de risco, analistas institucionais — necessitam não apenas do número, mas do raciocínio que o sustenta. A ausência desta camada limita o ticket médio e a profundidade de adoção enterprise.

## 2.1 Gap Identificado na Jornada B2B

O endpoint /v1/consensus/{event_id} (ADR-008) retorna IGCI, participant_count e average_reputation. Esses dados são suficientes para validação de demanda com os 5 fundos parceiros do piloto, mas insuficientes para contratação enterprise de longo prazo. O feedback esperado dos fundos parceiros nos primeiros 30 dias de piloto incluirá a pergunta: "Por que o consenso está em 72%? Quais fatores estão influenciando?" O scenario-engine é a resposta arquitetural a essa pergunta.

## 2.2 Dependências Estruturais Não Satisfeitas (Justificativa do DEFERRED)
| **Dependência**                             | **Status Atual**              | **Impacto se Ausente**                             |
| ------------------------------------------- | ----------------------------- | -------------------------------------------------- |
| IGCI com dados reais de usuários            | Inexistente — pré-launch    | Narrativa sem ancoragem real — sem valor         |
| ConsensusHistory acumulado (série temporal) | Schema existe, dados ausentes | Sem histórico de variação para contextualizar      |
| NCS operacional (ADR-010)                   | Não implementado              | Narrativa sem contexto factual de eventos          |
| Track record de resoluções (≥ 60 dias)      | Inexistente — pré-launch    | Sem evidência de calibração para validar narrativa |
| API B2B funcional (ADR-008)                 | Em implementação              | Sem canal de entrega do produto ao cliente         |

# 📄 3. Decisão

> O iPYSY implementará um microserviço scenario-engine (porta 9018) que consome o tópico ipysy.consensus.updated via Kafka, consulta o histórico de ConsensusHistory via REST interno (read-only), integra contexto do NCS via Redis, e utiliza quarkus-langchain4j para geração de narrativa estruturada via LLM API externa. O serviço persiste cenários gerados em tabela própria no TimescaleDB e os expõe via extensão do endpoint B2B existente (/v1/consensus/{event_id}/scenarios). A implementação inicia após 3 meses de operação real pós-launch, quando as dependências estruturais estiverem satisfeitas.

## 4.4 ConsensusUpdatedConsumer — Trigger Principal

O ConsensusUpdatedConsumer é o ponto de entrada do scenario-engine. Consome o tópico ipysy.consensus.updated (já produzido pelo ConsensusProducer existente) e aplica o DeltaFilter antes de qualquer processamento custoso.

```java
// ConsensusUpdatedConsumer.java
@ApplicationScoped
@Slf4j
public class ConsensusUpdatedConsumer {
	
    @Inject ScenarioService scenarioService;
    @Inject DeltaFilter deltaFilter;
    
	@Incoming("consensus-updated-in")
	@Acknowledgment(Acknowledgment.Strategy.MANUAL)
	public CompletionStage<Void> consume(Message<ConsensusUpdatedMessage> message) {
		ConsensusUpdatedMessage event = message.getPayload();
		
		// Filtro 1: apenas mudanças significativas de IGCI
		if (!deltaFilter.shouldTrigger(event)) {
			log.debug("Δ IGCI abaixo do threshold --- ignorando eventId=", event.getRelatedEventId());
			return message.ack();
		}
		
		// Filtro 2: apenas razões de atualização que geram contexto válido
		if (!deltaFilter.isRelevantReason(event.getReason())) {
			return message.ack();
		}
		
		log.info("Trigger válido: eventId= IGCI → Δ=",
			event.getRelatedEventId(),
			event.getPreviousConsensusScore(),
			event.getNewConsensusScore(),
			event.getNewConsensusScore().subtract(event.getPreviousConsensusScore()));
			
		return scenarioService.generateScenario(event)
			.thenCompose(result -> message.ack())
			.exceptionally(ex -> {
				log.error("Falha na geração de cenário para eventId=:",
					event.getRelatedEventId(), ex.getMessage(), ex);
				// NACK → DLQ, não bloqueia o consumer
				message.nack(ex);
				return null;
			});
	}
}
```

## 4.5 DeltaFilter — Controle de Threshold

```java
// DeltaFilter.java
@ApplicationScoped
public class DeltaFilter {
	
	// Configurável via application.properties
	// scenario.trigger.delta.threshold=0.05 (5 pontos percentuais)
	@ConfigProperty(name = "scenario.trigger.delta.threshold", defaultValue = "0.05")
	BigDecimal threshold;
	
	// Cooldown: não regerar cenário para o mesmo evento em menos de N minutos
	@ConfigProperty(name = "scenario.trigger.cooldown.minutes", defaultValue = "30")
	int cooldownMinutes;
	
	@Inject ScenarioResultRepository repository;
	
	public boolean shouldTrigger(ConsensusUpdatedMessage event) {
		BigDecimal delta = event.getNewConsensusScore()
			.subtract(event.getPreviousConsensusScore())
			.abs();
		
		if (delta.compareTo(threshold) < 0) return false;
		
		// Verificar cooldown
		Optional<ScenarioResult> last = repository.findLatestByEventId(
			event.getRelatedEventId());
		if (last.isPresent()) {
			Instant cooldownBoundary = Instant.now()
				.minus(cooldownMinutes, ChronoUnit.MINUTES);
			if (last.get().getCreatedAt().isAfter(cooldownBoundary)) {
				return false; // dentro do cooldown
			}
		}
		return true;
	}
	
	public boolean isRelevantReason(String reason) {
		return Set.of("prediction_added", "reputation_updated").contains(reason);
	}
}
```

## 4.7 LlmGateway — Abstração do Provedor LLM

O LlmGateway abstrai o provedor LLM via quarkus-langchain4j, permitindo troca de provedor sem alteração nos consumidores. A configuração do provedor é feita via application.properties.

```java
// LlmGateway.java
@ApplicationScoped
public class LlmGateway {

    @Inject
    @RestClient
    AnthropicLlmClient anthropicClient; // gerado pelo quarkus-langchain4j

    @ConfigProperty(name = "scenario.llm.provider", defaultValue = "anthropic")
    String provider;

    @ConfigProperty(name = "scenario.llm.model", defaultValue = "claude-haiku-4-5-20251001")
    String model;

    @ConfigProperty(name = "scenario.llm.max.tokens", defaultValue = "1024")
    int maxTokens;

    @Timeout(value = 30, unit = ChronoUnit.SECONDS)
    @Retry(maxRetries = 2, delay = 2000)
    public CompletableFuture<String> generateAsync(String prompt) {
        long start = System.currentTimeMillis();
        return anthropicClient.complete(model, prompt, maxTokens)
            .whenComplete((result, ex) -> {
                long elapsed = System.currentTimeMillis() - start;
                if (ex != null) {
                    log.error("LLM call failed after {}ms: {}", elapsed, ex.getMessage());
                } else {
                    log.info("LLM call completed in {}ms, model={}", elapsed, model);
                }
            });
    }
}
```

## 4.8 ScenarioValidator — Guardrail de Coerência

O ScenarioValidator é o componente de segurança que garante que a narrativa gerada pelo LLM nunca contradiz o IGCI. É executado após cada chamada LLM antes de qualquer persistência.

```java
// ScenarioValidator.java
@ApplicationScoped
public class ScenarioValidator {

    private static final BigDecimal TOLERANCE = new BigDecimal("0.001");

    public ValidationResult validate(ParsedScenario scenario, BigDecimal igci) {

        // Regra 1: probabilidade do cenário dominante DEVE ser = IGCI
        BigDecimal diff = scenario.getDominantProbability().subtract(igci).abs();
        if (diff.compareTo(TOLERANCE) > 0) {
            return ValidationResult.inconsistent(
                String.format("dominant_probability=%s diverge do IGCI=%s",
                    scenario.getDominantProbability(), igci));
        }

        // Regra 2: soma das probabilidades alternativas <= (1 - IGCI)
        BigDecimal altSum = scenario.getAlternativeScenarios().stream()
            .map(ParsedAlternative::getProbability)
            .reduce(BigDecimal.ZERO, BigDecimal::add);
        if (altSum.compareTo(BigDecimal.ONE.subtract(igci).add(TOLERANCE)) > 0) {
            return ValidationResult.inconsistent("soma de alternativas excede 1 - IGCI");
        }

        // Regra 3: narrativa dominante não pode conter linguagem de previsão alternativa
        String dominant = scenario.getNarrativeDominant().toLowerCase();
        List<String> forbidden = List.of("improvável", "não deve", "dificilmente",
            "provavelmente não", "baixa probabilidade");
        for (String word : forbidden) {
            if (dominant.contains(word)) {
                return ValidationResult.inconsistent(
                    "linguagem conflitante na narrativa dominante: '" + word + "'");
            }
        }

        // Regra 4: pelo menos 1 driver identificado
        if (scenario.getDrivers() == null || scenario.getDrivers().isEmpty()) {
            return ValidationResult.inconsistent("nenhum driver identificado");
        }

        return ValidationResult.valid();
    }
}
```

# 📄 6. Regras Arquiteturais Invioláveis

> PRINCÍPIOS QUE NÃO PODEM SER VIOLADOS EM NENHUMA CIRCUNSTÂNCIA

| **#** | **Regra**                                                                                                                                                       | **Consequência da Violação**                                               |
| ----- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| R-01  | O scenario-engine NUNCA escreve, modifica ou chama endpoints de escrita do consensus-service, reputation-service ou qualquer componente do Core v3.2            | Invalidação da auditabilidade do IGCI — quebra do ADR-006                  |
| R-02  | A probabilidade do cenário dominante DEVE ser matematicamente igual ao IGCI do momento da geração (tolerância: ±0.001)                                          | Contradição com o Core — narrativa passa a ser previsão alternativa ilegal |
| R-03  | A narrativa NUNCA deve usar linguagem que sugira que a probabilidade do IGCI está errada ou que um resultado mais provável existe fora do consenso              | Desinformação ao cliente B2B — risco regulatório e reputacional            |
| R-04  | A chave da API LLM NUNCA deve ser commitada no repositório — apenas via variável de ambiente ANTHROPIC_API_KEY ou equivalente                                   | Exposição de credencial — replica o incidente .env.prod já identificado    |
| R-05  | O scenario-engine é o ÚNICO serviço autorizado a ler o tópico ipysy.consensus.updated com group.id scenario-engine-group                                        | Conflito de consumer group com resolution-service ou outros consumidores   |
| R-06  | O ScenarioValidator deve rejeitar (status: inconsistent) e registrar qualquer cenário que viole R-02 ou R-03, sem propagar o resultado inválido ao endpoint B2B | Output corrompido entregue ao cliente — perda de confiança                 |
| R-07  | Prompts são versionados e imutáveis após deploy. Mudança de prompt implica nova versão (v1.x) e novo campo llm_prompt_version no ScenarioResult                 | Impossibilidade de auditoria retroativa de cenários gerados                |
| R-08  | O scenario-engine não expõe dados de usuários individuais — os cenários são sempre agregados e anonimizados (compliance ADR-007)                                | Violação LGPD/GDPR — passivo regulatório em due diligence                  |

# 📄 12. Posicionamento Estratégico — iPYSY Decision OS

Este ADR formaliza tecnicamente o que o brainstorming estratégico de março de 2026 identificou conceitualmente como "iPYSY Decision OS". A camada de simulação narrativa não é uma feature — é o terceiro pilar do produto B2B:

| **Pilar**           | **Componente**                | **O que entrega ao cliente B2B**                                                                                                                                              |
| ------------------- | ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1 — Medição         | Core v3.2 + IGCI              | "A probabilidade é 72%" — número auditável e calibrado                                                                                                                        |
| 2 — Contexto        | NCS (ADR-010)                 | "Os sinais que alimentam esse consenso são X, Y, Z" — factual                                                                                                                 |
| 3 — Explicação      | scenario-engine (este ADR)    | "Os 3 cenários que levam a esse resultado e seus drivers" — narrativo                                                                                                         |

A combinação dos três pilares transforma o iPYSY de "plataforma de previsão" para "infraestrutura de antecipação de decisões" — posicionamento de produto que o brainstorm estratégico rotulou como iPYSY Decision OS. O scenario-engine é o componente que torna esse posicionamento tecnicamente defensável.

> **DIFERENCIAL COMPETITIVO:** O MiroFish (e qualquer sistema baseado exclusivamente em simulação LLM) pode gerar narrativas, mas não pode ancorá-las em probabilidade auditável calibrada por histórico real de previsores. O iPYSY faz o inverso — parte do número correto e o explica. Essa inversão é o moat.
