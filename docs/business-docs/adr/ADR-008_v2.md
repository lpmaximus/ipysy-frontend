# 📄 1. Contexto e Problema

O PRD-001 original não contemplava nenhuma história de usuário B2B. O cliente institucional — analista de fundo, gestor de risco, consultoria estratégica — não estava representado no produto. Sem um endpoint de API funcional, a iPYSY não consegue iniciar o processo de validação comercial com parceiros institucionais nem construir o track record de 6 meses exigido por clientes B2B.

> **PRINCÍPIO ARQUITETURAL CENTRAL:** A API de consenso B2B opera exclusivamente sobre a camada de dados de saída já calculada pelo CORE v3.2. A API nunca acessa, modifica ou consulta o Core diretamente. O CORE v3.2 permanece completamente congelado e inalterado, conforme mandato do ADR-006.

# 📄 2. Decisão

O sistema iPYSY implementará um endpoint REST de consulta de consenso agregado, autenticado por API Key individual por parceiro, com documentação Swagger/OpenAPI, para ser disponibilizado em modo piloto controlado para até 5 fundos parceiros por 30 dias.

A decisão é implementar o mínimo funcional que permita validar demanda real antes de qualquer investimento em automação ou escala. O endpoint pode ser servido com dados calculados manualmente nas primeiras semanas, evoluindo para consulta direta ao banco de dados de saída do Core conforme o volume justificar.

# 📄 3. Especificação Técnica

## 3.1 Endpoints do Piloto

| **Endpoint**             | **Método** | **Descrição**                                                                      |
| ------------------------ | ---------- | ---------------------------------------------------------------------------------- |
| /v1/events               | GET        | Lista eventos disponíveis no piloto, com filtro opcional por categoria             |
| /v1/consensus/{event_id} | GET        | Retorna o IGCI atual, número de participantes e nível médio de reputação do evento |

## 3.2 Autenticação — API Key por Parceiro

Cada fundo parceiro recebe uma API Key única gerada internamente. A chave deve ser enviada no header de todas as requisições:

```http
GET /v1/consensus/evt_001
Host: api.ipysy.com
X-API-Key: ipysy_pk_FUND_XXXXXXXXXXXXXXXX
Accept: application/json
```

* API Keys geradas manualmente pelo time de Engenharia durante o piloto
* Uma chave por fundo — sem compartilhamento
* Requisições sem X-API-Key válido retornam HTTP 401 Unauthorized
* Rate limit: 1.000 requisições/dia por chave (revisável conforme uso)

## Observações sobre o campo thumbnail_url:

* Retorna null quando nenhum thumbnail foi enviado para o evento — campo sempre presente no schema, nunca ausente.
* thumbnail_key (path interno no MinIO) nunca é retornado na API — é campo de infraestrutura interna.
* Para eventos MULTICLASS, o array outcomes inclui thumbnail_url individual por outcome.

## 3.5 Códigos de Resposta HTTP

| **Código** | **Status**            | **Descrição**                                        |
| ---------- | --------------------- | ---------------------------------------------------- |
| 200        | OK                    | Requisição bem-sucedida. Dados retornados no body.   |
| 401        | Unauthorized          | API Key ausente ou inválida.                         |
| 403        | Forbidden             | API Key válida, mas sem acesso ao evento solicitado. |
| 404        | Not Found             | event_id não encontrado ou não disponível no piloto. |
| 429        | Too Many Requests     | Rate limit excedido (1.000 req/dia).                 |
| 500        | Internal Server Error | Erro interno. Time notificado automaticamente.       |

# 📄 6. Conformidade com LGPD/GDPR

O endpoint de consenso expõe exclusivamente dados agregados e anonimizados, em plena conformidade com o ADR-007:

* IGCI: média ponderada das previsões — nunca uma previsão individual
* Número de participantes: contagem total — nunca identificações
* Nível médio de reputação: média do grupo — nunca score individual
* thumbnail_url: URL de imagem do contrato ou outcome — não contém dados pessoais
* Nenhum user_id, ghost_id, nome ou e-mail é exposto pela API

# 📄 8. Alternativas Consideradas e Rejeitadas

As alternativas consideradas para a API B2B são as mesmas da v1 e permanecem rejeitadas. A extensão com campo thumbnail_url não altera a decisão arquitetural central — a API opera exclusivamente sobre dados de saída calculados, nunca acessando o Core diretamente.

# 📄 9. Declaração Final

O ADR-008 v2 estende o schema de resposta da API de Consenso B2B para incluir o campo thumbnail_url nos endpoints /v1/consensus/{event_id} e /v1/events, em conformidade com o ADR-015 (Padrão de Mídia e Armazenamento MinIO). A decisão arquitetural central permanece inalterada: a API opera exclusivamente sobre dados de saída calculados pelo CORE v3.2, que permanece congelado. O campo thumbnail_key (path interno no MinIO) nunca é exposto na API.
