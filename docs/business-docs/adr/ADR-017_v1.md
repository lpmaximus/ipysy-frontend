# 📄 1. Contexto e Motivação

O mockup do iPYSY (v3, arquivo **260507_ipysy-mockup.html**) define telas de dashboard analítico para o usuário — em especial a tela B2-04 (Calibração do Consenso) e telas de perfil Free e Premium. Essas telas exibem:

* Curva de Calibração Histórica (reliability diagram) com dois consensos sobrepostos
* Brier Score médio como indicador de desempenho individual
* Decomposição Murphy (UNC / REL / RES) para diagnóstico de calibração
* Histograma de Sharpness (distribuição das probabilidades previstas)
* Série temporal do Brier Score (rolling 90 dias)
* Percentil do usuário vs. plataforma

A auditoria do backend (versão **260509_ipysy-backend-main**) revelou que:

* O Prediction Service já possui GET /predictions/me/brier-score com BrierScoreResponse
* O Reputation Service já armazena brierScore por domínio em UserDomainStats (calculado incrementalmente)
* Todos os dados necessários estão na tabela predictions (predictedValue, accuracy, resolvedAt)
* Nenhum dos 5 endpoints de analytics está implementado — apenas o Brier Score global

> Este ADR registra a decisão de implementar os endpoints faltantes sem alterações de schema de banco de dados, aproveitando os dados já persistidos.

# 📄 2. Decisão

O iPYSY **adiciona 5 novos endpoints** no **Prediction Service** para suportar as telas de analytics do mockup. Todos os cálculos são realizados on-demand a partir da tabela predictions existente, sem novos campos de banco de dados. O Brier Score por domínio expõe o campo já existente em UserDomainStats via novo endpoint no Reputation Service.

> **Decisão complementar:** a Curva de Calibração do Consenso (Consenso Geral vs. Consenso Calibrado EVT L3+) é responsabilidade do Consensus Service, não do Prediction Service, pois requer agrupamento de todas as previsões por evento e ponderação pelo IGCI.

# 📄 4. Especificação dos Novos Endpoints

## 4.1 Curva de Calibração Individual

Retorna os pontos da curva de calibração (reliability diagram) do usuário autenticado, agrupados em bins de 10%.

| **Endpoint**      | **GET /api/v1/predictions/me/calibration**                                                                                                                                                                              |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Autenticação**  | Bearer token — @Authenticated                                                                                                                                                                                           |
| **Plano mínimo**  | FREE (curva própria) / PREMIUM (com benchmark de consenso)                                                                                                                                                              |
| **Descrição**     | Curva de calibração individual. Cada ponto representa um bin de 10% de probabilidade prevista.                                                                                                                          |
| **Query params**  | *domain (string, opcional) — filtra por domínio temático horizonDays (int, opcional, default: todos) — filtra previsões com horizonte <= N dias*                                                                        |
| **Response body** | *List<CalibrationPointDTO> record CalibrationPointDTO( BigDecimal binCenter, // ex: 0.05, 0.15, ..., 0.95 BigDecimal actualFrequency, // frequência real de outcome=1 no bin int count // número de previsões no bin )* |

Lógica de negócio (PredictionService):

* Buscar todas as predictions do userId com status = RESOLVED
* Para cada prediction: outcome_binary = accuracy >= 0.5 ? 1 : 0
* Agrupar em 10 bins: bin_k = floor(predictedValue × 10) / 10 + 0.05
* Para cada bin: binCenter = média dos predictedValue, actualFrequency = média dos outcome_binary, count = n
* Retornar apenas bins com count >= 1 (omitir bins vazios)
* Se horizonDays presente: filtrar por DATEDIFF(resolvedAt, createdAt) \<= horizonDays

# 📄 5. Matemática dos Cálculos

## 5.1 Brier Score

O Brier Score mede o erro quadrático médio entre probabilidade prevista e resultado real. Menor é melhor.

$$
BS = (1/N) × Σᵢ (fᵢ − oᵢ)²
$$

Onde:

* fᵢ = probabilidade prevista pelo usuário (campo predictedValue, escala 0.0--1.0)
* oᵢ = resultado real (derivado: accuracy >= 0.5 → 1, caso contrário → 0)
* N = número total de previsões resolvidas

| **Brier Score**    | **Interpretação**       | **Referência**                                             |
| ------------------ | ----------------------- | ---------------------------------------------------------- |
| < 0.10             | **Elite**               | Nível Superforecaster (Good Judgment Project)              |
| 0.10 -- 0.18       | Excelente               | Top 15% da plataforma estimado                             |
| 0.18 -- 0.25       | Bom                     | Acima da média — BS do mockup: 0.18 (consenso calibrado)   |
| 0.25               | **Baseline (50/50)**    | Equivale a sempre dizer 50% — sem valor preditivo          |
| > 0.25             | **Abaixo do chute**     | Pior que não prever nada                                   |

## 5.2 Decomposição de Murphy

A decomposição de Murphy separa o Brier Score em três termos independentes, cada um explicando uma dimensão do desempenho:

$$
BS = UNC − RES + REL
$$
$$
UNC — Incerteza (Uncertainty)
$$
$$
UNC = ō × (1 − ō)
$$

Onde ō é a frequência base de ocorrência de eventos (proporção de outcomes=1 em todo o conjunto). Representa a dificuldade intrínseca das questões, independente do previsor. Questões 50/50 têm UNC máxima de 0.25.

**REL — Reliability (Calibração)**

$$
REL = (1/N) × Σₖ nₖ × (f̄ₖ − ōₖ)²
$$

Onde k = índice do bin, nₖ = previsões no bin, f̄ₖ = probabilidade média no bin, ōₖ = frequência real no bin. Mede o desvio entre probabilidades previstas e frequências observadas. Menor é melhor. REL = 0 significa calibração perfeita.

$$
RES — Resolution (Discriminação)
$$
$$
RES = (1/N) × Σₖ nₖ × (ōₖ − ō)²
$$

Mede o quanto o previsor separa eventos que ocorrem dos que não ocorrem. Maior é melhor. RES = 0 significa que o previsor não agrega informação além da frequência base (equivale a sempre dizer ō).

Interpretação para o usuário:

* REL alto → você usa probabilidades que não refletem a realidade → corrija suas âncoras
* RES baixo → você não diferencia bem os eventos → seja mais decisivo nas extremidades
* BS melhora com REL ↓ e RES ↑ simultaneamente

## 5.3 Algoritmo de Binning (Curva de Calibração)

Pseudocódigo Java para o **PredictionService**:

```java
List<CalibrationPointDTO> buildCalibrationCurve(UUID userId, String domain, Integer horizonDays) {

  // 1. Buscar previsões resolvidas
  List<Prediction> preds = repo.findResolved(userId, domain, horizonDays);

  // 2. Inicializar 10 bins [0.0, 0.1), [0.1, 0.2), ..., [0.9, 1.0]
  double[] sumX = new double[10], sumY = new double[10];
  int[] count = new int[10];

  // 3. Preencher bins
  for (Prediction p : preds) {
    double f = p.predictedValue.doubleValue();
    double o = p.accuracy.compareTo(0.5) >= 0 ? 1.0 : 0.0;
    int bin = Math.min((int)(f * 10), 9);
    sumX[bin] += f; sumY[bin] += o; count[bin]++;
  }

  // 4. Calcular centros e frequências
  List<CalibrationPointDTO> points = new ArrayList<>();
  for (int k = 0; k < 10; k++) {
    if (count[k] == 0) continue;

    points.add(new CalibrationPointDTO(
    BigDecimal.valueOf(sumX[k] / count[k]), // binCenter
    BigDecimal.valueOf(sumY[k] / count[k]), // actualFrequency

    count[k]));
  }

  return points;
}
```

# 📄 6. Considerações de Performance

Todos os endpoints do Prediction Service percorrem a tabela predictions para o userId. Com volume esperado de até 10.000 previsões por usuário no médio prazo, as queries são viáveis on-demand. Os índices existentes (idx_user, idx_status) já cobrem os filtros necessários.

Para escala futura (> 100k previsões/usuário), recomendar:

* Materializar CalibrationSnapshot via Kafka Consumer no Analytics Service após cada EventResolvedConsumer
* Armazenar resultado pré-calculado em Redis com TTL de 1 hora (suficiente para dashboard)
* O Analytics Service já consome ReputationUpdatedConsumer — adicionar PredictionCalculatedConsumer é extensão natural

Esta materialização está fora do escopo deste ADR e será tratada em ADR futuro caso o volume justifique.

# 📄 7. Alternativas Consideradas

| **Alternativa**                        | **Prós**                                         | **Razão para não adotar**                                                                          |

# 📄 9. Critérios de Aceite

* GET /me/calibration retorna 10 bins com binCenter, actualFrequency e count para usuário com ≥ 20 previsões resolvidas
* GET /me/murphy retorna UNC + REL + RES onde BS = UNC - RES + REL com precisão de 4 casas decimais
* GET /me/sharpness retorna 10 bins cobrindo todo o range [0, 1] com variância calculada
* GET /me/brier-score/history retorna pontos ordenados cronologicamente sem gaps no range solicitado
* GET /me/ranking/percentile retorna percentile no range [0, 100] consistente com ranking global
* Todos os endpoints retornam 401 sem token válido
* Endpoints marcados PREMIUM retornam 403 para usuários Free
* Filtro ?domain= reduz o conjunto de previsões sem alterar a lógica de cálculo
* Performance: qualquer endpoint responde em < 500ms para usuário com até 1.000 previsões resolvidas
