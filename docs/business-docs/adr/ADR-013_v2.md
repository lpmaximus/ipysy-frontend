# 1. Contexto e Motivação

O Core v3.2 do iPYSY foi projetado e implementado para eventos binários: cada evento tem exatamente dois outcomes possíveis (ocorre / não ocorre), e cada previsão individual é um escalar pᵢ ∈ [0,1] representando a probabilidade do outcome positivo.

A análise comparativa com plataformas de referência do setor de inteligência preditiva (realizada em março de 2026) revelou quatro tipos de eventos que o mercado suporta: binário, multiclasse, numérico contínuo, numérico escalonado e condicional. O tipo multiclasse — eventos com N outcomes mutuamente exclusivos — é o segundo mais relevante em volume e em aplicação ao perfil do iPYSY, cobrindo casos como:

* Eleições com múltiplos candidatos (governadores, presidentes, prefeitos)
* Premiações culturais e esportivas (Oscar, Grammy, Copa, Champions League)
* Rankings e classificações (qual empresa liderará um setor, qual país crescerá mais)
* Cenários discretos com N possibilidades mutuamente exclusivas

O Core v3.2 não possui estrutura nativa para receber vetores de probabilidade nem para calcular consenso sobre múltiplos outcomes simultaneamente. Uma implementação ingênua (decomposição em K sub-eventos binários independentes) resolve o problema superficialmente, mas introduz três defeitos estruturais:

| **Defeito**              | **Descrição**                                                                               | **Impacto**                                                      |
| ------------------------ | ------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| Inflação de reputação    | A reputação do usuário é atualizada K vezes por um único evento — uma por sub-evento      | Eventos com muitos candidatos inflam artificialmente ΔR          |
| Fator 1/K como gambiarra | Requer divisão manual de ΔR por K para compensar — regra ad hoc fora do Core              | Débito técnico, não auditável, inconsistente com o modelo formal |
| Débito de migração       | Suporte futuro a alocação livre (vetor) exigiria redesign completo do schema e dos serviços | Bloqueio de evolução do produto                                  |

# 2. Princípio Arquitetural Fundamental

> O Core v3.2 é imutável. O ADR-013 NÃO altera nenhuma equação, parâmetro, constante ou implementação do ConsensusCalculator, ReputationCalculator ou ResolutionService existentes. A extensão opera exclusivamente na camada de adaptação de entrada e saída do pipeline de eventos.

Esta premissa preserva:

* A integridade do registro de propriedade intelectual do Core v3.2 (prova de anterioridade)
* A narrativa institucional de um engine imutável e auditável para investidores e clientes B2B
* A estabilidade do backend implementado em 20 microserviços
* A compatibilidade com todos os ADRs existentes (ADR-006 a ADR-015)

# 3. Definição do Problema

> **PROBLEMA CENTRAL:** Como suportar eventos com N outcomes mutuamente exclusivos no iPYSY sem alterar o Core v3.2, sem introduzir débito técnico no pipeline existente, e preservando a correção matemática do sistema de reputação?

## 3.1 Restrições de Projeto

| **Restrição**                             | **Descrição**                                                                                                                |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| R-1 Imutabilidade do Core                 | ConsensusCalculator.java, ReputationCalculator.java e ResolutionService.java não podem ser modificados em sua lógica central |
| R-2 Unicidade de atualização de reputação | Um evento, independente do número de outcomes, deve gerar exatamente uma atualização de reputação por usuário                |
| R-3 Extensibilidade futura                | A solução deve suportar alocação livre de probabilidades (vetor) sem redesign quando o produto evoluir                       |
| R-4 Compatibilidade de schema             | Novas migrations Flyway não podem quebrar dados existentes de eventos binários                                               |
| R-5 Soma do consenso                      | O IGCI multiclasse deve somar 100% quando o usuário vota em apenas um outcome (modo M0)                                      |

# 4. Decisão

> O iPYSY implementará suporte a eventos multiclasse por meio de uma Camada de Adaptação de Tipo de Evento (CATE), posicionada entre o frontend/API e o pipeline do Core v3.2. A CATE normaliza previsões multiclasse em representações compatíveis com o engine existente, aplica o Brier Score Multiclasse como função de erro nativa, e produz um vetor IGCI como saída. O Core v3.2 permanece matematicamente e estruturalmente intocado.

# 5. Extensão Matemática Formal

> **Seção inalterada em relação à v1 — ver documento de referência para formulação completa de p⃗ᵢ, BSᵢ, κᵢ, ΔRᵢ e C⃗(e)ₖ.) A extensão matemática opera exclusivamente na CATE, sem modificar qualquer equação do Core v3.2.**

## 5.1 Modos de Entrada Suportados

| **Modo**                | **Representação**                            | **Aplicação**                         | **Status**              |
| ----------------------- | -------------------------------------------- | ------------------------------------- | ----------------------- |
| Voto único (M0)         | p⃗ᵢ = (0,...,1,...,0) — vetor canônico   U | suário escolhe 1 candidato          M | 0 — implementar agora |
| Alocação livre (futuro) | p⃗ᵢ = (0.35, 0.25, 0.20, 0.20)               | Usuário distribui % entre outcomes    | Pós-M0 — sem redesign |

# 6. Arquitetura da Camada de Adaptação de Tipo de Evento (CATE)

## 6.1 Componentes da CATE

| **Componente**        | **Responsabilidade**                                                                 | **Serviço**        | **Impacto no código existente**                                  |
| --------------------- | ------------------------------------------------------------------------------------ | ------------------ | ---------------------------------------------------------------- |
| EventTypeRouter       | Identifica se o evento é BINARY ou MULTICLASS via campo event_type                   | event-service      | Novo campo — migration Flyway V18                              |
| EventVectorBuilder    | Constrói p⃗ᵢ a partir do voto único do usuário; converte para vetor canônico         | prediction-service | Nova classe — não altera PredictionService existente           |
| OutcomeValidator      | Valida que o outcome escolhido existe no evento; rejeita outcomes inválidos          | prediction-service | Nova classe — sem impacto                                      |
| BrierScoreCalculator  | Calcula BSᵢ = (1/K) · Σₖ (pᵢₖ - Yₖ)²; entrega εᵢ equivalente ao ReputationCalculator | reputation-service | Nova classe — substitui cálculo de εᵢ para eventos MULTICLASS  |
| EntropyConfidenceCalc | Calcula κᵢ via entropia normalizada; retorna 1.0 em modo voto único                  | reputation-service | Nova classe — sem impacto em eventos binários                  |
| IGCIVectorSerializer  | Serializa C⃗(e) como mapa outcome → probabilidade para Kafka e API                   | consensus-service  | Extensão do ConsensusProducer — não altera ConsensusCalculator |
| OutcomeRegistry       | Persiste a lista de K outcomes de cada evento multiclasse                            | event-service      | Nova tabela event_outcomes — migration Flyway V18              |

## 6.2 Regras Arquiteturais Invioláveis

| **#**                    | **Regra** | **Consequência da Violação**                                                         |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| R-01                     | ConsensusCalculator.java NÃO pode ser modificado para suportar multiclasse — a adaptação é feita na CATE antes de chegar ao calculator      | Invalida imutabilidade do Core v3.2 e o registro de IP                              |
| R-02                     | A reputação DEVE ser atualizada exatamente UMA vez por evento multiclasse — nunca K vezes                                                   | Inflação de reputação destrói a calibração do sistema reputacional                  |
| R-03                     | O BrierScoreCalculator DEVE produzir BSᵢ ∈ [0,1] — mesmo intervalo de εᵢ — para compatibilidade com os limiares θ₁ e θ₂ do Core v3.2   Re | gimes de recompensa/penalidade produzem resultados incorretos                       |
| R-04                     | Eventos BINARY existentes NÃO são afetados pela migration V18 — o campo event_type tem DEFAULT 'BINARY' e outcome_key é nullable         Qu | ebra de dados históricos e regressão nos testes existentes                          |
| R-05                     | O OutcomeValidator DEVE rejeitar previsões para outcomes não cadastrados em event_outcomes antes de persistir                                 | Corrupção do vetor de consenso com outcomes fantasma                                |
| R-06                     | Após o prazo de abertura de previsões, NENHUM novo outcome pode ser adicionado ao evento multiclasse                                          | Usuários anteriores não previram o novo outcome — vetor de consenso inconsistente |

## 6.3 Schema de Banco de Dados — Migrations Flyway

> **ALTERAÇÃO v2 — Migrations V19 e V20 adicionadas ao roadmap. Documentam os campos de thumbnail em events e event_outcomes, conforme ADR-015 (Padrão de Mídia e Armazenamento MinIO).**

### Migration V18 (inalterada — definida na v1 deste ADR)

```sql
-- V18__multiclass_event_support.sql

-- 1. Adicionar tipo ao evento (não quebra dados binários existentes)
ALTER TABLE events
  ADD COLUMN event_type VARCHAR(16) NOT NULL DEFAULT 'BINARY'
                        CHECK (event_type IN ('BINARY', 'MULTICLASS', 'NUMERIC'));

-- 2. Tabela de outcomes para eventos multiclasse
CREATE TABLE event_outcomes (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  event_id    UUID NOT NULL REFERENCES events(id) ON DELETE CASCADE,
  outcome_key VARCHAR(64) NOT NULL,   -- ex: 'candidate_a', 'candidate_b'
  label       VARCHAR(255) NOT NULL,  -- ex: 'Candidato A', 'Candidato B'
  position    INTEGER NOT NULL,       -- ordem de exibição (0-indexed)
  is_winner   BOOLEAN,                -- preenchido na resolução
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  UNIQUE (event_id, outcome_key)
);

-- 3. Previsões: adicionar coluna de outcome para eventos multiclasse
ALTER TABLE predictions
  ADD COLUMN outcome_key VARCHAR(64);  -- NULL para eventos binários (compatibilidade)

-- Constraint: outcome_key obrigatório para eventos MULTICLASS
-- (validado na camada de aplicação — OutcomeValidator)

-- 4. Índices
CREATE INDEX idx_event_outcomes_event ON event_outcomes(event_id);
CREATE INDEX idx_predictions_outcome ON predictions(event_id, outcome_key)
  WHERE outcome_key IS NOT NULL;
```

### Migration V19 — Thumbnail na tabela events (novo — ADR-015):

```sql
-- V19__event_thumbnail.sql

-- Adicionado pelo ADR-015 (Padrão de Mídia e Armazenamento MinIO)
ALTER TABLE events
  ADD COLUMN thumbnail_url VARCHAR(512), -- URL pública/presigned do MinIO
  ADD COLUMN thumbnail_key VARCHAR(512); -- path interno no bucket (gerenciamento interno)

-- Índice para lookup reverso (limpeza e auditoria de assets)
CREATE INDEX idx_events_thumbnail_key ON events(thumbnail_key)
  WHERE thumbnail_key IS NOT NULL;
```

### Migration V20 — Thumbnail na tabela event_outcomes (novo — ADR-015):

```sql
-- V20__outcome_thumbnail.sql
-- Adicionado pelo ADR-015 (Padrão de Mídia e Armazenamento MinIO)
-- Aplica-se à tabela criada na V18 — sem breaking changes
ALTER TABLE event_outcomes
  ADD COLUMN thumbnail_url VARCHAR(512), -- URL pública/presigned do MinIO por outcome
  ADD COLUMN thumbnail_key VARCHAR(512); -- path interno no bucket MinIO

-- Índice para lookup reverso
CREATE INDEX idx_outcomes_thumbnail_key ON event_outcomes(thumbnail_key)
WHERE thumbnail_key IS NOT NULL;
```

| **Campo**     | **Tabela**     | **Obrigatoriedade**                 | **Descrição**                                                               |
| ------------- | -------------- | ----------------------------------- | --------------------------------------------------------------------------- |
| thumbnail_url | events         | Opcional (BINARY)\                  | URL do MinIO exposta na API. Null quando ausente.                           |

# 8. Alternativa Considerada e Rejeitada

## 8.1 Opção A — Decomposição em K Sub-eventos Binários

| **Critério**                    | **Opção A (K sub-eventos)**                                 | **Opção B / ADR-013 (CATE)**                      |
| ------------------------------- | ----------------------------------------------------------- | ------------------------------------------------- |
| Atualização de reputação        | K vezes por evento — inflação proporcional a K              | 1 vez por evento — matematicamente correto        |
| Fator 1/K                       | Necessário como correção ad hoc — débito técnico            | Desnecessário — eliminado por design              |
| Suporte a alocação livre futura | Requer redesign completo de schema e serviços               | Nativo — sem alteração ao migrar para vetor livre |
| Integridade do Core v3.2        | Indiretamente violada: fator 1/K está fora do modelo formal | Preservada integralmente                          |
| Complexidade de resolução       | Resolução em cascata: K sub-eventos precisam fechar juntos  | Resolução atômica: um evento, um outcome vencedor |
| Débito técnico                  | Alto — regra especial não documentada no Core               | Zero — CATE é camada explícita e documentada      |
