## 1. Contexto

O Notification Service (9006) já entregava notificações via email (Quarkus Mailer) e SMS (Vonage
REST API), acionados por consumers Kafka. Faltava o terceiro canal: **push direto ao browser** para
todas as sessões abertas do usuário logado.

Casos de uso imediatos:
- Alerta resolvido → toast no browser do proprietário do alerta
- Evento criado → notificação a seguidores
- Plano atualizado → banner de boas-vindas ao novo tier
- Relatório assíncrono pronto → link de download (padrão futuro)

## 2. Decisão

**WebSocket via `quarkus-websockets-next`**, unidirecional (servidor → cliente) nesta fase.

### Por que WebSocket e não SSE?

| Critério                    | WebSocket                                | SSE                        |
| --------------------------- | ---------------------------------------- | -------------------------- |
| Suporte bidirecional futuro | ✅ nativo                                 | ❌ requer novo endpoint     |
| Quarkus 3.x suporte         | ✅ `quarkus-websockets-next`              | ✅ `@RestStreamElementType` |
| Vert.x proxy upgrade        | ✅ `HttpProxy` passa `Upgrade: websocket` | ✅ chunked                  |
| Múltiplas tabs/dispositivos | ✅ múltiplas conexões por userId          | ✅                          |
| Padrão relatório assíncrono | ✅ canal já aberto reutilizável           | ❌ requer polling           |

### Por que unidirecional nesta fase?

O modelo atual de notificações é exclusivamente push (servidor envia ao cliente). Mensagens
iniciadas pelo cliente são desnecessárias — predições, comentários, votos têm seus próprios
endpoints REST. A bidirecionalidade está disponível via `@OnTextMessage` quando necessária.

## 3. Arquitetura

```
Kafka topic (qualquer evento)
       ↓
Consumer existente no Notification (9006)
       ↓
NotificationService (orquestra email + SMS + WS)
   ↓                 ↓                     ↓
EmailService     SMSService         NotificationBroadcaster
(existente)      (existente)               ↓
                               WebSocketSessionRegistry
                               ConcurrentHashMap<UUID, Set<WebSocketConnection>>
                                             ↓
                                  browser(s) do usuário logado
```

### Fluxo de conexão WebSocket

```
1. Cliente: GET ws(s)://api.ipysy.com/ws/v1/notifications/{userId}?token={opaqueToken}
2. Gateway (GatewayRouter): roteia /ws/* → notification service (mesmo mecanismo /api/*)
              HttpProxy.reverseProxy() passa Upgrade: websocket nativamente
3. NotificationWebSocketEndpoint.onOpen():
   a. Extrai token do query param
   b. Chama SecurityServiceClient.introspect(token) → {userId, valid}
   c. Valida userId == token.userId && valid == true
   d. Registra WebSocketConnection no WebSocketSessionRegistry
4. NotificationBroadcaster.sendToUser(userId, payload):
   a. Busca Set<WebSocketConnection> do userId no registry
   b. Para cada conexão: conn.sendTextAndAwait(jsonPayload)
   c. Falha de envio: remove conexão do registry (stale cleanup)
```

## 4. Segurança

### Token Phantom Pattern

O token opaco (`opaqueToken`) é passado como query param `?token=` na URL de handshake WebSocket
(headers customizados não são suportados pela API WebSocket do browser).

Validação via `SecurityServiceClient.introspect(token)` → `GET /api/v1/security/internal/introspect?token={token}`

**Regras:**
- Token ausente → rejeitar imediatamente (sem chamar security service)
- `valid == false` → rejeitar
- `token.userId != path.userId` → rejeitar (impede userId spoofing)
- Security service indisponível → rejeitar (fail-closed)

**Mitigação de log:** never log o token — apenas `userId` e `connectionId`.

### CI-06 (ADR-015 — sem PII no payload)

O `WsNotificationPayload` contém apenas: `type`, `title`, `body`, `referenceId` (UUID do evento
ou alerta), `timestamp`. **Nunca** incluir email, telefone, CPF, endereço ou qualquer PII.

## 5. Payload WebSocket

```json
{
  "type": "ALERT_RESOLVED | EVENT_CREATED | PLAN_CHANGED | SEAL_VERIFIED | REPORT_READY | CUSTOM",
  "title": "Alerta resolvido",
  "body": "O evento 'PIB Q1 2026' foi resolvido como Sim.",
  "referenceId": "uuid-do-evento-ou-alerta",
  "timestamp": 1714900000000
}
```

## 6. Padrão de Relatório Assíncrono (futuro)

Quando um serviço processa um relatório pesado em background:

```
1. Cliente solicita: POST /api/v1/analytics/org/export → 202 Accepted {jobId}
2. Analytics service processa em background (minutos)
3. Ao concluir: publica ipysy.reports.ready no Kafka
4. NotificationBroadcaster recebe e chama sendToUser(userId, {
     type: "REPORT_READY",
     title: "Relatório pronto",
     body: "Seu relatório de analytics está disponível.",
     referenceId: presignedUrl  ← MinIO presigned URL (TTL 1h)
   })
5. Browser recebe mensagem WS → exibe notificação + botão de download
```

**Tópico Kafka**: `ipysy.reports.ready`
**Payload**: `{reportId, userId, downloadUrl (presigned MinIO), expiresAt}`
**TTL presigned URL**: 3600 segundos (1 hora) — configurável via `minio.presigned.ttl-seconds`

## 8. Dependência: Security Service

O endpoint `GET /api/v1/security/internal/introspect?token={token}` deve existir no
`security-service` (9001). Se não existir, precisa ser criado com:
- Lookup do token opaco no Redis
- Retorno `{userId: String, valid: boolean}`
- `@RolesAllowed("internal")` ou auth por IP interno

## 11. Decisões Rejeitadas

| Alternativa                    | Motivo da Rejeição                                                        |
| ------------------------------ | ------------------------------------------------------------------------- |
| SSE (`@RestStreamElementType`) | Unidirecional por design, sem reuso futuro bidirecional                   |
| Long polling                   | Latência alta, overhead de conexões, não escala                           |
| Firebase Cloud Messaging       | Dependência externa paga, dados saem da infraestrutura                    |
| Pusher / Ably                  | Idem — vendor lock-in, custo, PII concerns                                |
| WebSocket direto sem gateway   | Viola arquitetura Phantom Token — gateway deve ser único ponto de entrada |
