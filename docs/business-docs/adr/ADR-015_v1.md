# 📄 1. Contexto e Motivação

A análise comparativa com plataformas de referência do setor de inteligência preditiva — realizada em maio de 2026 — identificou que Kalshi e Polymarket operam com dois níveis de imagem por evento:

* Thumbnail do evento — imagem principal que representa o contrato, exibida no card de listagem e no cabeçalho da tela de detalhe.
* Thumbnail por outcome — miniatura individual de cada opção/variável, exibida ao lado de cada outcome em eventos multiclasse (ex.: foto do candidato em eleições, logo do time em eventos esportivos).

Paralelamente, o especialista de infraestrutura da iPYSY formalizou a seguinte diretriz arquitetural:

> **DIRETRIZ ARQUITETURAL — ESPECIALISTA DE INFRAESTRUTURA**
> Toda e qualquer imagem ou mídia que for feito upload — seja em evento ou em qualquer outra entidade da plataforma — deve ser gravada no MinIO, que é o S3-Compatible Object Storage onde a iPYSY armazena arquivos de upload. Esta regra é inviolável e se aplica a todos os microserviços e todos os fluxos de criação de conteúdo.

> O MinIO já está operacional em produção, utilizado como vault de backup LGPD no fluxo de anonimização (ADR-007 / CON-002 v4). Este ADR formaliza sua expansão como infraestrutura central de armazenamento de mídia da plataforma.

# 📄 2. Decisão

O iPYSY adota o MinIO (S3-Compatible Object Storage) como infraestrutura exclusiva de armazenamento para toda e qualquer mídia enviada por upload na plataforma. Ficam criados dois campos de mídia na camada de dados: thumbnail_url e thumbnail_key na tabela events (migration V19) e na tabela event_outcomes (migration V20). A thumbnail_url é exposta pela API; a thumbnail_key é campo interno de gerenciamento, nunca exposto ao consumidor.

# 📄 3. Regra Global de Armazenamento de Mídia

A regra se aplica sem exceção a todas as entidades da plataforma que suportem upload de arquivos, presentes ou futuras:

| **Entidade**              | **Tipo de Mídia**              | **Bucket Path (MinIO)**                       | **Status**          |
| ------------------------- | ------------------------------ | --------------------------------------------- | ------------------- |
| Eventos (events)          | Thumbnail do contrato          | events/thumbnails/{event_id}/cover.webp       | V19 — este ADR      |
| Outcomes (event_outcomes) | Thumbnail por opção/variável   | events/outcomes/{event_id}/{outcome_key}.webp | V20 — este ADR      |
| Perfil de usuário         | Foto de avatar                 | users/avatars/{user_id}/avatar.webp           | Futuro — a definir  |
| Insights B2B              | Imagens em conteúdo editorial  | insights/media/{insight_id}/{filename}        | Futuro — a definir  |
| Documentos KYC            | Docs identidade (já existente) | kyc/docs/{user_id}/{filename}                 | Existente — ADR-007 |
| Qualquer outro upload     | A definir por domínio          | dominio/tipo/{entity_id}/{filename}           | Regra padrão        |

Regras de nomenclatura e formato:

* Formato preferencial: WebP (melhor relação qualidade/tamanho para imagens de interface).
* Fallback aceito: JPEG, PNG.
* Nomes de arquivo em lowercase, sem espaços, sem acentos.
* Versão otimizada gerada automaticamente pelo serviço de upload (redimensionamento e compressão).
* URLs externas não são aceitas como fonte definitiva de mídia — todo conteúdo deve passar pelo pipeline de upload MinIO.

# 📄 4. Schema de Banco de Dados

## 4.1 Migration V19 — Thumbnail na Tabela events

Adiciona os campos de mídia à tabela events, sem quebrar dados existentes (ambas as colunas são nullable):

```sql
-- V19__event_thumbnail.sql
ALTER TABLE events
  ADD COLUMN thumbnail_url VARCHAR(512), -- URL pública/presigned do MinIO
  ADD COLUMN thumbnail_key VARCHAR(512); -- path interno no bucket (para gerenciamento)

-- Índice para lookup reverso (limpeza e auditoria de assets)
CREATE INDEX idx_events_thumbnail_key ON events(thumbnail_key)
  WHERE thumbnail_key IS NOT NULL;
```

## 4.2 Migration V20 — Thumbnail na Tabela event_outcomes

Adiciona campos de mídia por outcome (tabela criada pelo ADR-013 / migration V18). Aplicável exclusivamente a eventos MULTICLASS:

```sql
-- V20__outcome_thumbnail.sql
ALTER TABLE event_outcomes
  ADD COLUMN thumbnail_url VARCHAR(512), -- URL pública/presigned do MinIO por opção
  ADD COLUMN thumbnail_key VARCHAR(512); -- path interno no bucket MinIO

-- Índice para lookup reverso
CREATE INDEX idx_outcomes_thumbnail_key ON event_outcomes(thumbnail_key)
  WHERE thumbnail_key IS NOT NULL;
```

## 4.3 Semântica dos Campos

| **Campo**     | **Tipo**     | **Obrigatoriedade**                               | **Descrição**                                                                                         |
| ------------- | ------------ | ------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| thumbnail_url | VARCHAR(512) | Opcional (BINARY)                                | URL pública ou presigned do objeto no MinIO. Exposta pela API REST.                                   |
|               |              | Obrigatório p/ destaque editorial                 |                                                                                                       |
| thumbnail_key | VARCHAR(512) | Preenchido automaticamente pelo serviço de upload | Path interno do objeto no bucket MinIO (ex: events/thumbnails/uuid/cover.webp). Nunca exposto na API. |

| **Tipo de Evento**           | **thumbnail_url (evento)** | **thumbnail_url por outcome**    | **Observação**                                            |

# 📄 6. Regras de Exposição na API

O campo thumbnail_key é interno ao backend e jamais deve ser retornado ao consumidor da API. Apenas thumbnail_url é exposta.

# 📄 7. Pipeline de Upload de Mídia

Todo upload de mídia deve seguir o pipeline abaixo, implementado no serviço responsável pela entidade (event-service, user-service, etc.):

| **Etapa** | **Ação**                                                                                    | **Responsável**                     |
| --------- | ------------------------------------------------------------------------------------------- | ----------------------------------- |
| 1         | Cliente envia arquivo via multipart/form-data para o endpoint de upload da entidade         | Frontend / API Gateway              |
| 2         | Serviço valida tipo (WebP/JPEG/PNG), tamanho máximo (2 MB) e dimensões mínimas (400×400 px) | event-service / serviço da entidade |
| 3         | Serviço gera thumbnail_key seguindo a convenção de path (seção 3)                           | event-service / serviço da entidade |
| 4         | Arquivo é enviado ao MinIO via SDK S3-Compatible                                            | event-service / serviço da entidade |
| 5         | MinIO retorna confirmação de armazenamento                                                  | MinIO                               |
| 6         | Serviço persiste thumbnail_url e thumbnail_key na entidade correspondente (TimescaleDB)     | event-service / serviço da entidade |
| 7         | Serviço retorna thumbnail_url ao cliente (nunca thumbnail_key)                              | event-service / serviço da entidade |

# 📄 9. Conformidade LGPD/GDPR

Thumbnails de eventos e outcomes não contêm dados pessoais identificáveis (PII) por definição — representam o contrato ou a opção, não o usuário. Aplicam-se as seguintes salvaguardas:

* Thumbnails de perfil de usuário (futuro) devem seguir o mesmo pipeline MinIO e são considerados dados de imagem pessoal — sujeitos ao regime de anonimização do ADR-007 em caso de exclusão de conta.
* Thumbnails de KYC (já existentes) continuam sob o regime vault do ADR-007, sem alteração.
* O thumbnail_key nunca deve ser exposto na API ou em logs acessíveis — é dado de infraestrutura interna.

# 📄 12. Declaração Final

O ADR-015 formaliza a regra arquitetural inviolável de que toda e qualquer mídia enviada por upload na plataforma iPYSY deve ser armazenada no MinIO (S3-Compatible Object Storage). Cria os campos thumbnail_url e thumbnail_key nas tabelas events (V19) e event_outcomes (V20), estabelece a convenção de bucket paths, define o pipeline de upload e as regras de exposição na API. O CORE v3.1 permanece matematicamente intocado. Os documentos EDT-003 v2, ADR-008 v2 e ADR-013 v2 são revisados em paralelo para refletir estas decisões.
