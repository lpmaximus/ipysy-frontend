# 📄 1. Contexto e Problema

O CORE IPYSY-v3.1 foi projetado como sistema determinístico, auditável e juridicamente defensável. Sua integridade depende da continuidade histórica dos dados de previsão e reputação — cada previsão contribui para o consenso IGCI e para o histórico de calibração do sistema.

O problema identificado durante a Sessão Estratégica do Conselho (Fev/2026) é a seguinte tensão estrutural:

| **Direito Legal (LGPD / GDPR)**<br>Art. 18 LGPD / Art. 17 GDPR garantem ao titular o direito de solicitar a exclusão de seus dados pessoais. A plataforma deve cumprir. | **Necessidade Técnica (CORE v3.1)**<br>Previsões históricas formam o consenso IGCI. Exclusão retroativa de previsões distorceria índices já publicados e auditados. |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

Adicionalmente, o GUIA COMPLICE PT identificou explicitamente este conflito como ponto crítico: 'Direito ao apagamento pode colidir com: nenhum contrato pode ser apagado'. A solução precisa satisfazer ambos os lados sem criar uma violação em nenhum deles.

# 📄 2. Decisão

> **O sistema iPYSY implementará uma rotina de pseudonimização progressiva com vault segregado, tratada como processo operacional interno — sem qualquer alteração no CORE v3.1, no ADR-006 ou nos fluxos de produto existentes.**

O princípio central é a separação entre identidade e contribuição:

* A identidade do usuário (PII: nome, e-mail, CPF/NIF, IP) é removida dos bancos principais.
* A contribuição matemática do usuário (previsões, peso no consenso) é preservada de forma anonimizada via ghost_id.
* Um registro cifrado é mantido em ambiente segregado (Vault) pelo prazo prescricional aplicável, para fins de defesa legal.

# 📄 3. Fluxo da Rotina — Ciclo de Vida Completo

| **Fase**                         | **Gatilho**                                                      | **Ação do Sistema**                                                                                    | **Estado dos Dados**                                                                  |
| -------------------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------- |
| **FASE 0**<br>**(Ativo)**        | Usuário ativo na plataforma                                      | Nenhuma. Operação normal do CORE v3.1.                                                                 | Dados pessoais + reputação vinculados ao user_id. Operação padrão.                    |
| **FASE 1**<br>**(Solicitação)**  | Usuário solicita exclusão de dados (Art. 18 LGPD / Art. 17 GDPR) | Dispara rotina ERASE_REQUEST. SLA: resposta em até 72h.                                                | Dados pessoais identificáveis pendentes de anonimização.                              |
| **FASE 2**<br>**(Anonimização)** | Confirmação da solicitação válida                                | Substitui user_id por ghost_id criptografado. Remove PII do banco principal.                           | PII removido. ghost_id mantido. Previsões históricas preservadas com ghost_id.        |
| **FASE 3**<br>**(Quarentena)**   | Imediato após Fase 2                                             | Replica dados cifrados para Vault segregado. Define TTL = data_exclusao + 5 anos.                      | Vault cifrado (AES-256). Acesso restrito. Auditável. Invisível para o produto.        |
| **FASE 4a**<br>**(Expiry)**      | TTL expirado sem litígio registrado                              | Job agendado executa DELETE físico no Vault.                                                           | Exclusão física definitiva e irreversível. Log de auditoria mantido (sem PII).        |
| **FASE 4b**<br>**(Litígio)**     | Ordem judicial ou defesa documentada antes do TTL                | DPO ativa acesso ao Vault mediante protocolo formal. Dados recuperados apenas para a finalidade legal. | Dado recuperado com controle de acesso e log completo. Retorna à quarentena após uso. |
PII significa Personally Identifiable Information.

## 3.1 Diagrama de Fluxo Resumido

```
Usuário solicita exclusão
         │
         ▼
[ROTINA: ERASE_REQUEST]
         │
         ├─── Valida solicitação (SLA: 72h)
         │
         ▼
[FASE 2: ANONIMIZAÇÃO --- Banco Principal]
  user_id ─────────────→ ghost_id (hash irreversível)
  PII (nome, email, CPF) ──→ REMOVIDO
  Previsões históricas ────→ MANTIDAS com ghost_id
  Reputação acumulada ─────→ MANTIDA (congelada)
         │
         ▼
[FASE 3: VAULT SEGREGADO]
Cópia cifrada (AES-256) ──→ TTL = hoje + 5 anos
Acesso: DPO + Jurídico apenas
Auditoria: log imutável de cada acesso
         │
         ├──── TTL expirado + sem litígio ──→ [FASE 4a] DELETE físico
         │
         └──── Ordem judicial / litígio ────→ [FASE 4b] Recuperação controlada
                                                          │
                                                          └→ Retorno ao Vault após uso
```

# 📄 4. Especificação Técnica

## 4.1 ghost_id — Estrutura e Geração

O ghost_id é um identificador pseudônimo gerado a partir do user_id original por meio de função de hash criptograficamente segura, com salt específico do ambiente de produção. Não é reversível sem acesso ao Vault.

```json
ghost_id = HMAC-SHA256(user_id, SALT_PRODUCAO)
// SALT_PRODUCAO: chave gerenciada via KMS (ex: AWS KMS / GCP Cloud KMS)
// ghost_id tem 64 chars hex, sem colisão para o volume esperado da plataforma
// Formato no banco: "ghost_" + ghost_id[:16] (ex: "ghost_a3f7b2c1d4e5f6a7")
```

## 4.2 Schema — Banco Principal (pós-anonimização)

```
-- ANTES da exclusão
users: { user_id, nome, email, cpf, created_at, reputation_score, ... }

-- APÓS a exclusão (Fase 2)
users: { ghost_id, created_at, reputation_score, status: "REMOVED" }
       -- colunas PII: nome, email, cpf → REMOVIDAS (ALTER TABLE + dados zerados)

predictions: { ghost_id, event_id, probability, created_at, brier_contribution }
             -- user_id substituído por ghost_id em toda a tabela
```

## 4.3 Vault Segregado — Requisitos de Infraestrutura

* Ambiente fisicamente separado do banco de produção (VPC isolada, sem peering direto).
* Criptografia em repouso: AES-256. Criptografia em trânsito: TLS 1.3.
* IAM restrito: acesso apenas pelo DPO e equipe jurídica designada, com MFA obrigatório.
* Toda operação no Vault gera log imutável (append-only) com: timestamp, operador, finalidade, referência legal.
* TTL gerenciado por job agendado (cron diário) com alerta automático 30 dias antes da expiry.
* Custo estimado de infraestrutura: mínimo (bucket S3/GCS cifrado + Lambda/Cloud Function para gestão de TTL).

## 4.4 Integração com o CORE v3.1 — O que NÃO muda

> **PRINCÍPIO ARQUITETURAL: O CORE v3.1 permanece completamente inalterado. Ele nunca conheceu user_id — apenas recebe previsões válidas e retorna atualizações de reputação. A substituição de user_id por ghost_id é transparente para o Core.**

O consenso IGCI já calculado para eventos resolvidos não é recalculado. O ghost_id carrega o peso histórico congelado no momento da exclusão, que decai naturalmente para zero ao longo do tempo conforme o mecanismo de decaimento por inatividade já previsto no CORE v3.1 (3% por período).

# 📄 6. Base Legal e Fundamentação Jurídica

## 6.1 Prazo de 5 Anos — Fundamentação
| **Fundamento Principal**       | Art. 206, §3º, IV do Código Civil (CC/2002) — Prescrição geral de pretensões pessoais: 3 anos. Adotamos 5 anos para margem adicional de segurança.                                    |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Fundamento Complementar BR** | GUIA COMPLICE BR-v1: 'Registro de logs por 5 anos' — alinhamento com prática recomendada de compliance.                                                                               |
| **Fundamento Complementar PT** | GDPR Art. 5(1)(e): dados mantidos apenas pelo tempo necessário. Prazo de 5 anos documentado e justificado na DPIA como necessário para defesa legal.                                    |
| **Base Legal para Retenção**   | LGPD Art. 16, II: 'Exclusão desnecessária de dados para cumprimento de obrigação legal ou regulatória'. Retenção cifrada em Vault = cumprimento de potencial obrigação legal de defesa. |
| **Base Legal GDPR**            | Art. 17(3)(e) GDPR: direito ao apagamento não se aplica quando necessário 'para efeitos de declaração, exercício ou defesa de um direito num processo judicial'.                        |

## 6.2 Consentimento e Transparência

A Política de Privacidade e os Termos de Uso devem ser atualizados para informar claramente ao usuário que, ao solicitar exclusão:

* Seus dados pessoais identificáveis serão removidos dos sistemas ativos em até 72 horas.
* Um registro anonimizado (sem qualquer dado que permita identificação direta) será mantido por até 5 anos para fins de integridade do sistema e defesa legal.
* Após esse prazo, a exclusão física será realizada automaticamente.

Essa comunicação deve ser feita no fluxo de solicitação de exclusão, antes da confirmação pelo usuário.

# 📄 7. Consequências e Trade-offs

## Consequências Positivas

* Resolve o passivo regulatório identificado pelo Conselho (Sessão Estratégica, Fev/2026) sem custo técnico para o Core.
* Permite comercialização B2B com conformidade LGPD/GDPR documentada — requisito para clientes institucionais.
* Protege a empresa juridicamente em caso de litígios futuros envolvendo ex-usuários.
* Preserva a integridade histórica do consenso IGCI — produto principal para clientes B2B.
* Custo operacional mínimo: a rotina é automatizada e o Vault tem custo marginal de infraestrutura.

## Consequências a Monitorar

* Aumento marginal de complexidade operacional: o DPO passa a ter responsabilidade formal sobre o Vault.
* Necessidade de atualização de documentos jurídicos (Política de Privacidade, DPIA para Portugal).
* O ghost_id precisa ser rastreado no schema do banco — equipe de engenharia deve garantir migração sem impacto em indexes e queries de performance.

# 📄 8. Alternativas Consideradas e Rejeitadas
| **Alternativa 1** | Exclusão física imediata e total — REJEITADA. Distorceria consensos históricos auditáveis. Inviabiliza defesa em litígios futuros.                 |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Alternativa 2** | Manter dados completos indefinidamente — REJEITADA. Violação direta do Art. 18 LGPD / Art. 17 GDPR. Passivo regulatório inaceitável.               |
| **Alternativa 3** | Anonimização sem Vault — REJEITADA. Elimina possibilidade de defesa legal. Risco jurídico alto sem benefício técnico adicional.                    |
| **Alternativa 4** | Solução escolhida: pseudonimização + Vault segregado com TTL — APROVADA. Equilibra conformidade legal, proteção jurídica e integridade do sistema. |

# 📄 10. Declaração Final

O ADR-007 resolve o passivo regulatório do direito ao esquecimento sem tocar no CORE IPYSY-v3.1 e sem criar qualquer quebra nos fluxos de produto existentes. A solução é implementada como rotina operacional interna, transparente para o usuário e para os sistemas de produto. O CORE v3.1 permanece congelado e inalterado, conforme mandato do ADR-006.

> Este ADR habilita a iPYSY a operar com conformidade total em Brasil e Portugal, protegendo juridicamente a empresa e seus clientes B2B, sem comprometer a qualidade ou integridade do consenso probabilístico que constitui o produto central da plataforma.
