# 📄 1. Contexto e Motivação

A integridade do sistema de reputação da iPYSY depende fundamentalmente de um princípio: cada pessoa real corresponde a exatamente uma conta. O sistema de Score Reputacional (ADR-006, CORE v3.1) pondera as previsões de cada usuário com base em seu histórico verificável. Se uma mesma pessoa operar com múltiplas contas, ela pode:

* Inflacionar artificialmente seu score ao abandonar contas com desempenho ruim;
* Manipular o consenso coletivo por meio de múltiplas identidades;
* Contornar bloqueios, penalidades ou restrições aplicadas a uma conta;
* Comprometer a auditabilidade do histórico reputacional que os clientes B2B compram.

A pesquisa de mercado sobre plataformas reguladas de previsão demonstrou que a solução mais eficaz para garantir unicidade combina: verificação de e-mail, verificação de telefone via OTP, coleta de dados pessoais (nome, data de nascimento, endereço, documento nacional) e verificação biométrica de identidade por documento oficial.

Este ADR define a arquitetura, o fluxo e as decisões técnicas do módulo de verificação de identidade e unicidade de usuário da iPYSY, complementando o ADR-007 (pseudonimização/LGPD) e o ADR-006 (sistema reputacional).

# 📄 2. Definição do Problema

> **PROBLEMA CENTRAL: Como garantir que cada pessoa física possua exatamente uma conta ativa no iPYSY, sem criar fricção excessiva para usuários legítimos, e em conformidade com LGPD/GDPR?**

## 2.1 Vetores de Ataque à Unicidade
| **Vetor**                     | **Mecanismo**                                 | **Risco** |
| ----------------------------- | --------------------------------------------- | --------- |
| Multi-conta por e-mail        | Criação de múltiplos e-mails descartáveis     | ALTO      |
| Multi-conta por telefone      | Uso de chips pré-pagos ou VoIP                | MÉDIO     |
| Multi-conta por documento     | Uso de documentos falsos ou de terceiros      | ALTO      |
| Conta abandonada + nova conta | Usuário com conta suspensa cria nova          | MÉDIO     |
| Uso de VPN/proxy              | Mascaramento de IP para burlar geolocalização | BAIXO     |

# 📄 3. Decisão

> O iPYSY implementará um fluxo de onboarding em 4 etapas progressivas de verificação, com unicidade garantida por hash de documento nacional (CPF/NIF) e por biometria facial via provedor externo. Nenhuma conta pode ser ativada para previsões sem completar o Nível 3 (verificação de identidade). O Nível 4 (biometria) é obrigatório para acesso Premium e para mercados que exigem KYC reforçado.

## 3.1 Referência: Fluxo de Onboarding em Plataformas Reguladas

A pesquisa de mercado em plataformas reguladas de previsão identificou as seguintes etapas como padrão de mercado para onboarding seguro:

1.  Tela Login / Sign-up — ponto de entrada com opções OAuth (Google, Apple) ou e-mail
2.  sign-up/email — coleta de e-mail
3.  sign-up/password — criação de senha com requisitos de segurança
4.  sign-up/verify — verificação de código OTP enviado ao e-mail
5.  sign-up/phone-number — coleta de número de telefone (com campo de promo code)
6.  sign-up/phone-verify — verificação OTP de 4 dígitos via SMS (TwilioVerify)
7.  sign-up/profile — nome legal (first + last name)
8.  sign-up/birthday — data de nascimento (mínimo 18 anos, exigência federal)
9.  sign-up/profile — endereço completo (país, rua, cidade, estado, CEP, National ID)
10. sign-up/review-needed — aplicação em revisão
11. sign-up/identity — verificação KYC por documento oficial + biometria (Socure)
12. Continue on your phone — handoff para celular via SMS ou QR Code para captura do documento
13. Verificação concluída no celular — confirmação via SDK do provedor de identidade

Plataformas reguladas de referência utilizam dois provedores especializados: TwilioVerify para OTP de telefone e Socure para verificação de identidade (KYC) com biometria. O fluxo apresenta uma barra de progresso em 3 segmentos, tornando o processo claro e administrável para o usuário.

# 📄 5. Mecanismo de Unicidade

## 5.1 Estratégia de Hash de Documento

O mecanismo central de unicidade é o hash criptográfico do documento nacional (CPF para Brasil, NIF para Portugal). O documento nunca é armazenado em texto claro no banco principal.

> **doc_hash = HMAC-SHA256(normalizar(cpf_ou_nif), SALT_UNICIDADE) // SALT_UNICIDADE: chave gerenciada via KMS, diferente do SALT do ADR-007 // Normalização: remoção de pontos, traços e espaços. CPF: 11 dígitos. NIF: 9 dígitos. // doc_hash: 64 chars hex, único por documento real. // Coluna no banco: UNIQUE INDEX em doc_hash_verified (só preenchida após KYC aprovado)**

## 5.2 Camadas de Unicidade — Defesa em Profundidade
| **Camada**                      | **Verificação**                                       | **Bloqueio se duplicado**                   |
| ------------------------------- | ----------------------------------------------------- | ------------------------------------------- |
| 1 — E-mail                    | Unique index na coluna email                          | Imediato na tela de cadastro                |
| 2 — Telefone                  | Unique index + TwilioVerify Lookup (detecta VoIP)     | Bloqueio na etapa de telefone               |
| 3 — Documento Nacional        | HMAC-SHA256(CPF/NIF) com UNIQUE INDEX                 | Bloqueio após KYC — antes de ativar conta |
| 4 — Biometria Facial          | Socure: deduplicação por face (liveness + match)      | Bloqueio pelo Socure + webhook ao backend   |
| 5 — Nome + Data de Nascimento | Fuzzy match no banco (camada de alerta, não bloqueio) | Flag para revisão manual se score alto      |

## 5.3 Fluxo de Detecção de Duplicata

Quando uma duplicata é detectada pelo hash do documento ou pela biometria do Socure, o sistema executa o seguinte protocolo:

14. O backend recebe o sinal de duplicata (via verificação de hash local ou webhook Socure).
15. O sistema verifica o status da conta existente: ativa, suspensa ou com processo de exclusão em andamento (ADR-007).
16. Se a conta existente estiver ativa: bloqueia a nova criação e direciona para /sign-up/duplicate-detected.
17. Se a conta existente estiver suspensa: bloqueia e oferece canal de suporte para contestação.
18. Se a conta existente estiver em fase de exclusão/anonimização (ADR-007 Fase 2+): permite criação de nova conta somente após confirmação do DPO de que a anonimização foi concluída.
19. Todos os eventos são registrados em log imutável de auditoria com timestamp, IP e identificador da sessão.

> **RECOMENDAÇÃO PARA BRASIL:** Avaliar Unico Check como provedor primário de KYC. Possui integração nativa com a Receita Federal para validação de CPF, base biométrica brasileira robusta e conformidade explícita com a LGPD — vantagens significativas sobre provedores americanos no mercado local.

# 📄 7. Relação com ADR-007 (Pseudonimização / LGPD)

Este ADR e o ADR-007 formam um par complementar. A interação entre eles deve ser explicitamente gerenciada:

| **Aspecto**                    | **ADR-007 (Exclusão / LGPD)**                                  | **ADR-009 (Unicidade / KYC)**                                                   |
| ------------------------------ | -------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Propósito do CPF/NIF           | Removido como PII na anonimização                              | Hash armazenado permanentemente para garantir unicidade                         |
| Salt utilizado                 | SALT_PRODUCAO (para ghost_id)                                  | SALT_UNICIDADE (chave separada, gerenciada via KMS)                             |
| Quando o hash é criado         | N/A (CPF é removido na exclusão)                               | No momento da verificação KYC aprovada                                          |
| O hash persiste após exclusão? | Sim — coluna doc_hash_verified mantida após anonimização       | SIM — isso é intencional e necessário para impedir recadastro imediato          |
| Conflito LGPD                  | Possível — hash de documento pode ser considerado dado pessoal | Mitigação: uso de HMAC com salt secreto torna o hash não reversível sem a chave |
| Resolução do conflito          | DPO deve validar que HMAC com salt = dado anonimizado          | Parecer jurídico recomendado antes do go-live                                   |

> **ATENÇÃO — PONTO CRÍTICO LEGAL:** A retenção do doc_hash após a exclusão do usuário (para impedir recadastro) pode entrar em conflito com o 'direito ao esquecimento' da LGPD/GDPR. O DPO deve emitir parecer formal sobre se HMAC-SHA256 com salt secreto constitui anonimização suficiente. Este ADR recomenda a obtenção deste parecer como critério de aceitação obrigatório antes do go-live.

# 📄 8. Alternativas Consideradas e Rejeitadas
| **Alternativa**                                     | **Descrição**                                               | **Motivo da Rejeição**                                                                                                             |
| --------------------------------------------------- | ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Verificação apenas por e-mail                       | Unicidade garantida somente pelo e-mail                     | Trivialmente contornável com e-mails descartáveis. Insuficiente para sistema reputacional sério.                                   |
| Verificação apenas por telefone                     | OTP de SMS como único fator de unicidade                    | Chips pré-pagos são facilmente obtidos. Não garante unicidade de pessoa física.                                                    |
| KYC por terceiro sem hash local                     | Delegar unicidade 100% ao Socure                            | Cria dependência crítica de fornecedor. Sem controle interno. Risco de custo e lock-in.                                            |
| Biometria obrigatória para todos desde o início     | Todos os usuários fazem KYC biométrico para qualquer acesso | Fricção excessiva destrói conversão. Usuários iPYSY Free não precisam deste nível. Contradiz estratégia de crescimento orgânico.   |
| Verificação por CPF via Receita Federal diretamente | Consulta direta à API Datavalid/Serpro                      | Custo por consulta elevado. Cobertura limitada a Brasil. Não escalável internacionalmente. Mantido como camada adicional opcional. |

# 📄 9. Princípios de UX do Fluxo de Verificação

Com base em padrões de mercado de plataformas reguladas e boas práticas de UX para fluxos de verificação, os seguintes princípios devem guiar a implementação do fluxo iPYSY:

* Barra de progresso visível: 3 segmentos claros (Credenciais / Dados Pessoais / Identidade). O usuário sempre sabe onde está e quanto falta.
* Uma coisa por tela: cada etapa faz exatamente uma pergunta. Sem sobrecarga cognitiva.
* Botão 'Continue' desabilitado até validação completa: feedback visual imediato de erros de formato.
* Linguagem humana: 'What's your email?' em vez de 'Informe seu endereço de e-mail'. Adaptar para PT-BR com mesmo tom.
* Reenvio de código sempre disponível: máximo 3 reenvios por sessão, com cooldown de 60 segundos.
* Handoff mobile pensado: para KYC biométrico, oferecer SMS + QR Code. A maioria dos usuários faz a verificação de identidade no celular.
* Estados de espera comunicados: 'review-needed' com prazo claro (24h) e e-mail de notificação quando aprovado.
* Duplicata com saída digna: nunca expor qual conta existente está duplicando. Apenas indicar que já existe uma conta e oferecer canal de suporte.

# 📄 10. Requisitos Técnicos e de Implementação

## 10.1 Schema de Banco de Dados

> **-- Tabela principal de usuários users: {   user_id (UUID, PK),   email (UNIQUE),   phone_hash (UNIQUE, nullable),         -- hash do telefone verificado   doc_hash_verified (UNIQUE, nullable),  -- HMAC-SHA256(CPF/NIF, SALT_UNICIDADE)   face_id_ref (string, nullable),        -- referência Socure, não dado biométrico   verification_level (0|1|2|3|4),   kyc_status (pending|approved|rejected|review),   created_at, updated_at }  -- Índices críticos: UNIQUE INDEX ON users(email) UNIQUE INDEX ON users(phone_hash) WHERE phone_hash IS NOT NULL UNIQUE INDEX ON users(doc_hash_verified) WHERE doc_hash_verified IS NOT NULL**

## 10.2 Endpoint de Verificação de Unicidade

> **-- Verificação chamada ANTES de confirmar KYC ao usuário: POST /internal/identity/check-uniqueness Body: { doc_hash: string, face_id_ref: string } Response: {   is_unique: boolean,   conflict_reason: 'doc_hash' | 'face_biometric' | null,   existing_account_status: 'active' | 'suspended' | 'deleted' | null }**

## 10.3 Webhook Socure

O Socure envia um webhook ao backend iPYSY ao concluir a verificação. O backend deve:

* Processar o webhook em endpoint autenticado por HMAC-SHA256 com shared secret Socure;
* Extrair o status: approved / rejected / review;
* Chamar /internal/identity/check-uniqueness antes de atualizar o verification_level;
* Registrar o evento em log imutável de auditoria;
* Notificar o usuário por e-mail com o resultado.

# 📄 12. Trade-offs e Riscos
| **Trade-off**                            | **Custo**                                                 | **Benefício**                                                          | **Decisão**                                                                                   |
| ---------------------------------------- | --------------------------------------------------------- | ---------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Fricção no onboarding                    | Taxa de conversão menor vs. cadastro simples              | Sistema reputacional íntegro e auditável. Diferencial competitivo.     | ACEITO — a iPYSY vende confiança, não volume.                                               |
| Custo por verificação KYC                | Socure/Unico cobram por verificação (R\$ 1-5 por usuário) | Unicidade garantida. Proteção do consenso.                             | ACEITO — custo de aquisição justificado pelo modelo B2B.                                    |
| Retenção de doc_hash pós-exclusão        | Tensão com direito ao esquecimento LGPD/GDPR              | Impede recadastro imediato após exclusão para burlar penalidades.      | ACEITO com ressalva — sujeito a parecer do DPO.                                             |
| Dependência de provedor externo (Socure) | Lock-in, custo variável, risco de instabilidade           | Redução de complexidade interna, SLA enterprise, documentação robusta. | ACEITO — mitigado por arquitetura com interface abstrata de KYC (possível trocar provedor). |

# 📄 13. Declaração Final

O ADR-009 estabelece a arquitetura de verificação de identidade e unicidade do iPYSY, garantindo que cada pessoa física corresponda a exatamente uma conta ativa. A solução é baseada em padrões de mercado de plataformas reguladas, adaptada ao contexto regulatório brasileiro e português, e integrada aos ADR-006 e ADR-007 sem alterações no CORE v3.1. A integridade do sistema reputacional iPYSY — o produto central que os clientes B2B compram — depende diretamente da unicidade de usuário. Este ADR é, portanto, requisito arquitetural não negociável para o go-live da plataforma.
