# 1. Objetivo e Escopo

Este documento formaliza a estratégia de teste de stress para o endpoint de submissão de votações do iPYSY, simulando um ataque por volume — cenário em que centenas de usuários enviam previsões simultaneamente. O objetivo é mapear o comportamento do sistema além dos limites validados, identificar gargalos e confirmar que os mecanismos de proteção (rate limit, 2PC Narayana, backpressure Kafka) funcionam corretamente sob pressão extrema.

## 1.1 Contexto Técnico Relevante

O backend iPYSY processa cada votação por um pipeline que envolve: autenticação JWT (Keycloak), validação de unicidade (ghost_id), persistência em TimescaleDB via 2-Phase Commit (Narayana JTA), publicação no tópico Kafka ipysy.predictions, e atualização do IGCI pelo ConsensusCalculator com precisão BigDecimal. Cada etapa é um candidato a gargalo sob alto volume.

| **Componente**      | **Papel no fluxo de votação** | **Risco sob carga**                |
| ------------------- | ----------------------------- | ---------------------------------- |
| Keycloak JWT        | Autenticação de cada request  | **Saturação do token endpoint**    |
| PredictionService   | Validação + persistência      | **Contenção de threads Quarkus**   |
| Narayana JTA (2PC)  | Commit atômico Kafka + DB     | **Timeout sob alto I/O**           |
| Kafka (broker)      | Filanização assíncrona        | **Backpressure / lag crescente**   |
| ConsensusCalculator | Recálculo do IGCI             | **CPU-bound com BigDecimal**       |
| TimescaleDB         | Escrita de previsões          | **Lock contention em bulk writes** |
| Redis (cache)       | Leitura de IGCI               | **Baixo risco — read-heavy**     |
| Rate Limiter        | Proteção por IP/usuário       | **Esperado disparar na Fase 4**    |

# 2. Estratégia de Carga — 4 Fases

O script K6 executa quatro cenários progressivos. Cada fase tem objetivo distinto: as três primeiras validam o comportamento dentro dos limites conhecidos; a quarta fase simula intencionalmente um ataque além da capacidade validada para observar degradação controlada.

| **Fase**           | **VUs**   | **Duração** | **Objetivo**                           | **SLA Esperado**              |
| ------------------ | --------- | ----------- | -------------------------------------- | ----------------------------- |
| F1 — Aquecimento   | 0 → 50    | 1m30s       | Baseline e warm-up de JVM/GraalVM      | P95 \< 500ms, erro \< 1%      |
| F2 — Nominal       | 50 → 200  | 3m          | Carga de operação diária esperada      | P95 \< 800ms, erro \< 1%      |
| F3 — Stress/Pico   | 200 → 500 | 2m20s       | Evento viral — notícia de impacto      | P95 \< 1.5s, erro \< 5%       |
| F4 — Ataque Volume | 500 → 900 | 2m35s       | Além do limite validado — mapear falha | Observar degradação — sem SLA |

> **Baseline Validado (K6 anterior)**
>
> 700 VUs confirmados em teste anterior com 121 testes automatizados passando e 5 dashboards SigNoz ativos. A Fase 4 começa em 700 VUs e empurra até 900 para mapear o ponto de inflexão além desse limite.

# 4. Gargalos Esperados e Hipóteses

Com base na arquitetura conhecida do backend iPYSY (20 microserviços, Quarkus reactive, Narayana JTA, Kafka), os seguintes comportamentos são esperados durante o teste:

| **Gargalo**                          | **Sintoma Esperado**                           | **Fase em que ocorre**    | **Mitigação recomendada**                           |
| ------------------------------------ | ---------------------------------------------- | ------------------------- | --------------------------------------------------- |
| **ConsensusCalculator (BigDecimal)** | CPU spike, latência IGCI > 2s                F | 3 e F4                  T | hread pool sizing; cache de IGCI por TTL curto      |
| **Narayana JTA 2PC timeout**         | HTTP 409 crescente, erros de transação         | F3 e F4                   | Ajustar transaction timeout; monitorar XA log       |
| **Kafka consumer lag**               | Latência de atualização do IGCI aumenta        | F4                        | Aumentar partitions; ajustar consumer group threads |
| **Keycloak token endpoint**          | Latência de auth > 500ms; pool de conexões   F | 3 e F4                    | Cache de token no VU; aumentar DB pool do Keycloak  |
| **TimescaleDB write lock**           | P99 de latência de escrita explode             | F4                        | Checar connection pool size; índices de partição    |
| **Rate limiter (proteção)**          | HTTP 429 em cascata — esperado e correto       | F4                        | Confirmar que 429 não vira erro 5xx em cascata      |

> **Nota sobre HTTP 409 (Conflito Kafka/2PC)**
>
> O script trata HTTP 409 como comportamento ESPERADO do Narayana 2PC sob alta concorrência, NÃO como erro de produto. A métrica ipysy_conflitos_kafka rastreia esses casos separadamente. Se a taxa de 409 ultrapassar 15% na Fase 3, investigar timeout da transação XA.

# 6. Interpretação dos Resultados

Após execução, os resultados devem ser analisados por fase. A tabela abaixo é o guia de interpretação para o relatório gerado pelo handleSummary do script.

| **Sinal observado**          | **Interpretação**                                 | **Ação recomendada**                                           |
| ---------------------------- | ------------------------------------------------- | -------------------------------------------------------------- |
| P95 votação < 800ms na F2    | **Sistema dentro do SLA — PASS**                  | Nenhuma ação                                                   |
| P95 > 1.500ms na F3          | **Degradação sob stress — investigar gargalo**    | Checar SigNoz: CPU ConsensusCalculator e DB connections        |
| Taxa erros > 5% na F3        | **Regressão crítica — FAIL**                      | Bloquear go-live; investigar logs do PredictionService         |
| HTTP 409 > 15% na F3         | **Timeout XA ou deadlock no 2PC**                 | Ajustar narayana.transaction.timeout no application.properties |
| HTTP 429 crescente na F4     | **Rate limiter funcionando — CORRETO**            | Confirmar que não escala para 5xx; documentar limite efetivo   |
| Latência IGCI > 3s na F4     | **ConsensusCalculator saturado — esperado na F4** | Implementar cache Redis com TTL=5s para IGCI em alto volume    |
| Sistema não recupera após F4 | **Vazamento de memória ou thread starvation**     | Capturar heap dump e thread dump durante ramp-down             |

# 7. Relação com Critérios de Validação (Tríade de Validação)

Este teste é pré-requisito para a Tríade de Validação (Brier Score \< 0.20 por 3 meses + 500 eventos resolvidos + 2 LOIs B2B). O sistema precisa ser capaz de processar picos de votação sem perda de dados ou corrupção do IGCI — pois qualquer votação perdida afeta diretamente o cálculo do Brier Score dos usuários.

| **Critério da Tríade**          | **Conexão com este teste**                                      | **Risco se falhar**                 |
| ------------------------------- | --------------------------------------------------------------- | ----------------------------------- |
| Brier Score \< 0.20 por 3 meses | Votações perdidas ou duplicadas corrompem o BS individual       | **Tríade invalidada**               |
| 500+ eventos resolvidos         | Volume alto de resoluções simultâneas também é um pico de carga | **Gargalo idêntico ao teste**       |
| 2 LOIs B2B                      | Fundos exigem SLA e evidência de robustez técnica               | **Perda de credibilidade no pitch** |
