# 1. Objetivo e Escopo

Este documento formaliza a decisão de stack, arquitetura e estratégia de implementação do frontend do iPYSY, consolidando as decisões tomadas em staff review com a liderança técnica e de produto. O PRD-003 complementa o PRD-001 (histórias de usuário) e o PRD-002 (mapa de telas), constituindo a tríade de produto:

* PRD-001 — O quê: histórias de usuário e requisitos funcionais
* PRD-002 — Como aparece: mapa de telas e fluxos de navegação
* PRD-003 — Como é construído: arquitetura técnica, stack e estratégia de entrega

> **NOTA:** O PRD-003 estabelece padrões irrevogáveis de stack para o frontend do iPYSY. Alterações estruturais (troca de framework, mudança de estratégia de autenticação, alteração da arquitetura de deploy) requerem novo documento de decisão com aprovação do CEO e CTO.

# 2. Visão Estratégica — Dois Portais

O frontend do iPYSY não é uma interface única. É a camada de orquestração da experiência sobre uma arquitetura distribuída de 20+ microserviços, implementada sob um modelo híbrido de renderização:

| **Portal**                        | **Estratégia de Renderização**     | **Objetivo Principal**                                                                                                          |
| --------------------------------- | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Portal Público (ipysy.com)        | SSR — Server-Side Rendering        | SEO técnico, indexação, aquisição orgânica, exposição de dados públicos (eventos, rankings, conteúdo editorial)                 |
| Portal Privado (app.ipysy.com)    | SPA — Single Page Application      | Interatividade rica, dashboards operacionais, análises, interações sociais, consumo intensivo de dados em tempo real            |

Ambos os portais são implementados com um único código-base (Next.js 15), eliminando duplicação de lógica de negócio e garantindo consistência de marca.

# 3. Arquitetura Frontend

## 3.1 Modelo de Deploy

O frontend opera co-localizado com o backend no Hetzner Cloud (mesma rede interna, latência \< 1ms), expostos via Cloudflare Tunnel:

```
                [ Cloudflare CDN + Tunnel ] → www.ipysy.com
                                    ↓
              [ Frontend Next.js 15 — Docker Container — Hetzner ]
                                    ↓  (rede interna < 1ms)
                     [ API Gateway :8080 — Quarkus ]
                                    ↓
             [ 20 Microserviços + Kafka + Redis + TimescaleDB ]
```

> **NOTA:** O Kafka permanece exclusivamente no backend (comunicação entre microserviços). O frontend nunca acessa Kafka diretamente — recebe atualizações em tempo real via WebSocket, que são alimentadas por serviços backend que consomem Kafka internamente. Esta separação garante isolamento e segurança arquitetural.

## 3.2 Containerização e CI/CD

* Deploy via Docker com health check e restart policy unless-stopped — obrigatório antes do deploy em staging
* Pipeline CI/CD: GitHub Actions (principal) / CircleCI (fallback) — unificado com o pipeline backend existente
* Exposição pública: Cloudflare Tunnel → www.ipysy.com, sem necessidade de Cloudflare Pages
* Runbook de recovery do Cloudflare Tunnel documentado e testado antes do go-live

# 5. Autenticação — Phantom Token Pattern

## 5.1 Modelo de Segurança

A autenticação opera sob o Phantom Token Pattern com armazenamento de token exclusivamente em memória:

| **Componente**             | **Implementação**                                        | **Justificativa de Segurança**                                          |
| -------------------------- | -------------------------------------------------------- | ----------------------------------------------------------------------- |
| Token de acesso (opaco)    | Armazenado em memória — variável reativa Zustand/Next.js      | Inacessível a scripts maliciosos XSS; desaparece com reload (by design) |
| Refresh token              | httpOnly cookie gerenciado pelo Gateway                  | Invisível ao JavaScript por definição do browser; imune a XSS           |
| Validação                  | Redis cache no Security Service (~2-5ms)               E | limina latência de ida ao Keycloak em 95%+ das requisições              |
| Identidade                 | Keycloak como fonte de verdade                           | TTL Redis \< TTL Keycloak — garante propagação de revogações            |

## 5.2 Fluxo de Autenticação

```
Requisição normal (Cache HIT — 95%+ dos casos):
Frontend → Gateway → Security Service → [Redis HIT: ~2-5ms] → Token em memória

Cache MISS (< 5% dos casos):
Security Service → Keycloak (~80-150ms) → cacheia Redis → responde

Primeiro acesso / Reload (SSR):
Servidor Next.js → refresh silencioso via httpOnly cookie → repovoa store em memória → hydrate sem flash
```

> **NOTA:** O TTL do cache Redis é configurado menor que o TTL do token no Keycloak (ex: 10-12 minutos no Redis vs. 15 minutos no Keycloak), garantindo que revogações no Keycloak sejam eventualmente propagadas sem depender de invalidação ativa.

# 6. Tempo Real — WebSocket

## 6.1 Decisão de Protocolo

A decisão foi WebSocket nativo com usehooks-ts em detrimento de SSE (Server-Sent Events), pelas seguintes razões:

* Bidirecionalidade: o frontend pode iniciar processos e receber confirmação — caso de uso real no iPYSY para notificações de resolução de eventos e futuros relatórios assíncronos
* Canal único gerencia múltiplos tipos de notificação sem overhead de múltiplas conexões
* Fallback automático para long polling em caso de queda — transparente ao usuário

## 6.2 Escopo por Fase

| **Fase**              | **Escopo WebSocket**                                                                                             | **Critério de Aceite**                                                         |
| --------------------- | ---------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| MVP (Sprint 3)        | Canal único para notificações: alertas de resolução de eventos, notificações de reputação, broadcasts editoriais | Load test k6: 500 conexões simultâneas aprovado como gate de deploy em staging |
| Fase 2 (Sprint 3-4)   | Relatórios assíncronos pesados via WebSocket — geração em background com push ao cliente quando pronto           | Taxa de reconexão automática > 99,5% em produção (meta 90 dias)                |
| H1                    | Dashboards ao vivo, presença de usuários, feeds em tempo real                                                    | Definido no roadmap H1                                                         |

> **NOTA ARQUITETURAL:** O Consul atua como service discovery (descobre instâncias do serviço de notificação). O balanceamento com sticky sessions é responsabilidade do Load Balancer (ip_hash ou cookie-based), não do Consul diretamente.

# 7. Proteção do Código-Fonte

## 7.1 Objetivo e Premissa

O JavaScript entregue ao browser é inerentemente inspecionável. O objetivo desta estratégia não é tornar o código impenetrável, mas elevar o custo de engenharia reversa ao ponto de inviabilizar economicamente a cópia ou clonagem do produto, especialmente relevante para os módulos B2B e white-label do iPYSY.

> **PREMISSA CRÍTICA:** Premissa irrevogável: algoritmos de reputação (Brier Score), lógica de IGCI e regras de negócio sensíveis residem exclusivamente nos microserviços — nunca no bundle do cliente. A ofuscação protege a implementação da experiência, não os dados ou as regras de domínio.

## 7.2 Estratégia Diferenciada por Portal

| **Técnica**                            | **Portal Público**       | **Portal Privado** |
| -------------------------------------- | ------------------------ | ------------------ |
| **Minificação Terser agressiva**       | ✅ Aplicada               | ✅ Aplicada         |
| **Remoção de source maps do artefato** | ✅ Obrigatória            | ✅ Obrigatória      |
| **String array encoding (threshold)**  | ✅ threshold 0,5          | ✅ threshold 0,75   |
| **Control flow flattening**            | ❌ Impacta LCP/SEO        | ✅ threshold 0,5    |
| **Dead code injection**                | ❌ Aumenta bundle público | ✅ threshold 0,2    |
| **Self-defending**                     | ❌                        | ✅                  |
| **Verificação de domínio autorizado**  | ❌                        | ✅ Módulos B2B      |

## 7.3 Fluxo de Source Maps no CI/CD

> Build CI → Gera source maps → Upload para SigNoz → Delete do artefato → Deploy container
> _Gate automático: build falha se .map detectado no artefato final_

Source maps privados no SigNoz permitem que stack traces de erros sejam desobfuscados internamente para diagnóstico — sem expor o mapeamento ao usuário final.

* Mercado primário validado: Brasil — 2.300+ inscritos na waitlist
